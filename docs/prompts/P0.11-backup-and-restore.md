# P0.11 — Backup and restore

## Context
Read first: `CLAUDE.md`, **`docs/operations/backup-restore.md`
(authoritative)**, `docs/security.md`, `docs/gdpr.md` (backups), ADR 0014.
What exists already: database foundation incl. deletion ledger (P0.4), compose
with Garage (P0.2). Can be done in parallel with P0.5–P0.10.

## Goal
Backups and restores are automated, encrypted, verified every week, and
rehearsed from day one, for both the hosted service and self-hosters. A restore
never brings erased people back.

## Scope

### PostgreSQL backups (`infra/backup/`)
- pgBackRest container/sidecar with config generated from environment
  variables: S3 repository (endpoint, bucket, region, keys), `repo-cipher-type
  = aes-256-cbc` with passphrase from secrets, compression, retention (full
  weekly, differential daily, WAL archived continuously; retention to cover 35
  days of PITR plus monthly fulls for 12 months per the doc).
- Postgres configured with `archive_mode=on` and `archive_command` via
  pgBackRest; `archive_timeout` ≤ 5 min (RPO).
- Covers both databases (`clubadmin`, `zitadel`) — they share the cluster.
- Schedules run in the backup container (or the worker for status only);
  each run reports status to a `ops.backup_runs` table and a Prometheus metric.
- Dev compose profile `backup` targets the local Garage bucket.

### Object storage backups
- rclone job: copy/sync `clubadmin-files` to a second remote (separate
  credentials), with versioning enabled on the target. Status recorded as above.

### Immutability (hosted)
- Documentation and a check script for configuring the backup bucket at a
  provider **with S3 Object Lock** (compliance mode, retention = backup
  retention) and credentials that can write but not delete. `ops:verify-backup`
  warns if object lock is not active (Garage in dev does not support it; the
  check reports "not available" there).

### Verification (`pnpm ops:verify-backup`)
1. Start a temporary Postgres container.
2. Restore the latest backup (or `--time <timestamp>` for PITR).
3. Run checks: migrations table matches the expected version; row counts of
   key tables within expected deltas of production (from the last metrics
   snapshot); RLS enabled on all club tables; history triggers present;
   `pg_amcheck` on indexes; a sample of object keys referenced by the DB exist
   in the file backup.
4. **Replay the deletion ledger** and assert no erased person has non-anonymised
   data.
5. Record result in `ops.restore_verifications`; tear down.
- Scheduled weekly in the hosted environment; manual for self-hosters (also a
  documented cron example).

### Runbooks (`infra/backup/runbooks/`)
Step-by-step, copy-pasteable, tested in CI where possible:
1. Restore a single club's data from a point in time into a scratch database
   and extract it (uses per-club export when available; for now a documented
   SQL procedure filtering by `club_id`).
2. Point-in-time recovery of the whole cluster after a bad migration.
3. Total site loss: rebuild from IaC (placeholder steps), restore DB and files,
   re-point DNS.
4. Breach: preserve evidence, rebuild clean, restore from before the intrusion,
   rotate all secrets (list of every secret in the system), force re-login.
Each runbook ends with the deletion-ledger replay and the verification command.

### Admin visibility
- API endpoint for operators (and self-host admins): last successful backup,
  last verified restore, warnings when older than thresholds (24 h / 8 days).
  UI comes later; expose via `/api/v1/ops/backup-status` (operator permission)
  and a Prometheus alert rule example.

### CI
- Job: compose up Postgres + Garage + backup sidecar → seed `minimal` →
  full backup → write more data → WAL archive → destroy Postgres volume →
  restore → verify that rows written after the full backup are present (PITR)
  → run `ops:verify-backup`.

## Privacy and security
- Backup encryption keys never stored on the DB host in plain text; loaded
  from the secret store at runtime; key rotation documented.
- Backup credentials separate from application credentials.
- Restores into scratch environments are audited and torn down automatically.

## Protected identity
Restores preserve flags; verification checks that protected persons have no
stored address (constraint check).

## Locale and country packs
n/a.

## Performance
- Backup must not affect API latency budgets: pgBackRest with limited process
  count; measured during the load scenario.
- Restore of a 10 GB database < 30 min (documented target for RTO planning).

## Seed data
Uses `minimal` for CI.

## Acceptance criteria
- [ ] CI backup → destroy → restore → verify job passes, including PITR.
- [ ] Deletion ledger replay test: erase a person, restore an older backup, replay → person is anonymised again.
- [ ] `ops:verify-backup` reports clearly and stores results.
- [ ] Backup status endpoint shows last backup and verification.
- [ ] Runbooks complete and referenced from `docs/operations/backup-restore.md`.
- [ ] Self-hosting docs explain how to point backups at any S3-compatible target.

## Out of scope
Production IaC for the hosted service (separate private ops repo), per-club
export UI (P1.8/P1.2).
