# P1.1 — Sign-up, club creation, club managers, joining and invitations

## Context
Read first: `CLAUDE.md`, **ADR 0018 (authoritative)**, `docs/domain-model.md`
("Sign-up and joining", "club_role_assignments", "Effective permissions"),
ADR 0006/0025 (authorization), ADR 0020 (login email), ADR 0022 (protected
identity), ADR 0023 (global tables), ADR 0029 (API only grows),
ADR 0031 (entitlements, `club.created`), `docs/security.md`, `docs/gdpr.md`.

What exists already:
- **Sign-up and login (P0.6):** Zitadel sign-up with verified email;
  `IdentityService.provision` creates `account` + `person` on first login
  (rate-limited per IP). `people.birth_date` is unknown for self-signed-up
  people (`packages/db/src/schema/people.ts`).
- **Club creation (P0.5):** `OnboardingService.createClub` (club, creator as
  active member with member number 1, first `club_manager`, one
  transaction); `club.created` is published (P0.12; with billing on the
  worker starts the trial). `CLUB_CREATION` is in the config schema
  (`packages/server-kit/src/config.ts`) but nothing reads it.
- **Joining (P0.5):** `MembershipsService.joinClub` follows `join_policy`
  (`open` → active, `approval` → `applied` membership, `invite_only` →
  refused) and `approveMembership`. No endpoints.
- **Managers (P0.5):** `RolesService` assigns and ends roles,
  `proposeHandover` / `acceptHandover` / `declineHandover` /
  `cancelHandover` with audit events; the deferred constraint trigger
  `club_has_manager` keeps at least one active manager. No endpoints.
- **Schema only (P0.5):** `join_requests`, `invitations`
  (`packages/db/src/schema/joining.ts`). The demo data has rows for both
  (`docs/demodata`, `seed-data.md`: Nora's pending invitation, Camilla's
  request for Sofie, Henrik's request for Viktor).
- **Web (P0.9):** onboarding placeholder for people without clubs (Emma)
  with disabled "Find a club" / "Create a club" buttons.
- **Guardian invitations (P0.5)** return a secret token; only its hash is
  stored. No email is sent anywhere yet.

## Goal
A person can start without anyone's help: sign up, complete their profile,
then accept an invitation, find a club and ask to join (for themselves and
their children), or create a club and run it. Club managers handle join
requests, invite people by email, link or code, appoint further managers and
hand the role over. A club can never end up without a manager, and every step
is audited.

## Users and roles involved
Signed-up person without club, guardian (applying for wards), club manager,
registrar (join requests and member invitations), board chair (recovery),
platform operator (club-creation approval, recovery).

## User stories
- As a new user, I want to complete my profile (name, birth date) after
  sign-up, so the club gets correct age information.
- As a signed-up person, I want to search for clubs by name or place and ask
  to join, so I don't need an invitation.
- As a guardian, I want to apply for my child in the same request, giving
  preferred groups as a hint.
- As an applicant, I want to see and withdraw my pending requests.
- As a club manager or registrar, I want a list of pending join requests to
  approve or reject (with an optional message).
- As a club manager, I want to invite people by email, or create a link or a
  short code (optionally with a group or role preset, expiry and use limit),
  and revoke invitations.
- As an invited person, I want to open the link or enter the code, sign up or
  log in, and join the club with the presets applied.
- As a person allowed to create clubs, I want to create a club (name,
  country, time zone, locale, currency, join policy) and become its manager.
- As a club manager, I want to appoint and remove other managers, and hand
  over my role (successor accepts first).
- As a board chair of a club whose managers are all gone, I want to claim the
  manager role.
- As a platform operator, I want to approve club creation requests (when
  `CLUB_CREATION=approval`) and reassign a manager on documented request.

## Data model
- **`join_requests` becomes the only record of an application.** `approval`
  creates a pending join request (no `applied` membership); approving creates
  the active membership in the same transaction (via `MembershipsService`).
  Expand/contract: new code stops writing `applied`; a data migration turns
  existing `applied` memberships into pending join requests (keeping
  `created_at`; a matching pending request is reused). The `applied` status
  stays in the enum (ADR 0029: enums only grow) and is documented as
  legacy. Update ADR 0018 and `domain-model.md`.
- `join_requests`: add `decision_message` (shown to the applicant) and
  `withdrawn_at`. A request for several children is one row per child with
  the same `requested_by_person_id` (the unique pending index stays per
  person).
- `invitations`: add `code` handling. A code is 8 characters from an
  unambiguous alphabet, stored only as a hash in `token_hash` like links,
  rate-limited on lookup. `uses` counts acceptances (an email invitation has
  `max_uses = 1`). Add `invitation_acceptances`
  (`invitation_id`, `club_id`, `person_id`, `accepted_at`), so multi-use
  links record who joined, with history and RLS like other club tables.
- `club_creation_requests` (global, ADR 0023 RLS: the requester and
  platform operators): `requested_by_person_id`, the club fields, `status`
  (`pending`, `approved`, `rejected`, `withdrawn`), `decided_by_person_id`,
  `decided_at`, `decision_message`, `club_id` (once created). Only for
  `CLUB_CREATION=approval`.
- Every new table: `id` UUIDv7, `created_at`/`updated_at`, history, RLS,
  `updated_at` trigger, indexes for the queries below. Person IDs in new
  tables are declared in the module's `*.references.ts` (merges).
- Club search needs `clubs` columns that already exist (`name`,
  `short_name`, `address` for the place, `country`, `join_policy`,
  `status`). Add a trigram index (`pg_trgm`) on a normalised name expression;
  `invite_only` and non-active clubs never appear.

## API
All under `/api/v1`. Lists are keyset-paginated. Errors are problem details;
new domain error codes map to problem types in `docs/api/problems.md`.

| Method | Path | Permission | Notes |
|---|---|---|---|
| PUT | `/me/profile` | authenticated | Given name, family name, birth date (required once, then only via `person.profile.update` rules) |
| GET | `/clubs?q=&country=&cursor=` | authenticated | Search; listed clubs only (not `invite_only`, active); name, short name, place, join policy; rate-limited |
| POST | `/clubs` | `club.create` (platform) | `CLUB_CREATION=open` creates the club; `approval` creates a creation request (202); `operators_only` → operators only. Requires a completed profile |
| GET | `/me/club-creation-requests` | authenticated | Own requests |
| GET | `/ops/club-creation-requests` | `club.creation.decide` (platform) | Operators, MFA |
| POST | `/ops/club-creation-requests/:id/decision` | `club.creation.decide` | Approve (creates the club with the requester as manager) or reject |
| POST | `/clubs/:clubId/join-requests` | authenticated | For self and/or wards (guardian with `act_on_behalf`, checked in the service against the guardianship); `open` → active membership(s) directly; `invite_only` → 404 like any unlisted club |
| GET | `/me/join-requests` | authenticated | Own and wards' requests |
| POST | `/me/join-requests/:id/withdraw` | authenticated | Requester only |
| GET | `/clubs/:clubId/join-requests?status=&cursor=` | `club.join_requests.manage` | People via `PersonPresenter` |
| POST | `/clubs/:clubId/join-requests/:id/decision` | `club.join_requests.manage` | Approve (optional membership type) or reject, optional message |
| GET | `/clubs/:clubId/invitations?cursor=` | `club.invitations.manage` | Never returns tokens or codes after creation |
| POST | `/clubs/:clubId/invitations` | `club.invitations.manage` | Kind `email`/`link`/`code`; role presets only for club managers (`club.roles.manage`); returns the link or code once |
| POST | `/clubs/:clubId/invitations/:id/revoke` | `club.invitations.manage` | |
| GET | `/invitations/lookup?token=` or `?code=` | public | Club name and kind only; rate-limited per IP; expired, revoked or used up → 404 |
| POST | `/invitations/accept` | authenticated | Token or code; email invitations need the account's verified email to match; applies group and role presets; idempotent per person |
| GET | `/clubs/:clubId/managers` | `club.read` | Managers via `PersonPresenter` |
| POST | `/clubs/:clubId/managers` | `club.roles.manage` | Appoint (person must be an active member) |
| DELETE | `/clubs/:clubId/managers/:personId` | `club.roles.manage` | Remove or step down; last manager → `last_club_manager` problem |
| POST | `/clubs/:clubId/manager-handovers` | `club.roles.manage` | Propose successor (replaces an open proposal) |
| GET | `/me/manager-handovers` | authenticated | Open proposals to and from me |
| POST | `/manager-handovers/:id/accept` · `/decline` · `/cancel` | `club.handover.respond` (handover) | Successor accepts/declines, proposer cancels |
| POST | `/clubs/:clubId/managers/claim` | `club.managers.claim` | Board chair, only when the club has no active manager (MFA) |
| POST | `/ops/clubs/:clubId/managers` | `club.managers.reassign` (platform) | Operator, MFA, `reason` required (references the club's documented request) |

`GET /me/clubs` gains pending join requests and open handovers as
navigation hints (fields added, ADR 0029).

## Permissions
New permissions in `packages/shared/src/permissions.ts`, one policy each,
allow and deny tests, entries in the permission matrix (with tenant
isolation: a user of club B gets 404 for club A):
- `club.create` (platform): any account with a completed profile when
  `CLUB_CREATION=open` or `approval`; only platform operators (MFA) when
  `operators_only`. Defaults: `open` when `DEPLOYMENT_MODE=hosted`,
  `operators_only` when self-hosted (ADR 0018). Deny: unverified account,
  incomplete profile, non-operator in `operators_only`.
- `club.creation.decide` (platform): platform operators, MFA.
- `club.join_requests.manage` (club): club managers (MFA), registrars.
- `club.invitations.manage` (club): club managers (MFA), registrars
  (registrars cannot set role presets).
- `club.handover.respond` (handover): the successor (accept, decline), the
  proposer (cancel). Deny: anyone else, including other managers.
- `club.managers.claim` (club): an active `chair` when no active manager
  exists. Deny: any other role, or while a manager exists.
- `club.managers.reassign` (platform): platform operators, MFA. Never
  grants the operator access to club data.
- `club.roles.manage` already covers appointing and removing managers.

## UI (web)
- **Onboarding** (people without clubs, Emma): complete profile (birth date
  required), then three cards: "I have an invitation" (link or code),
  "Find a club", "Create a club" (hidden or explained when `club.create` is
  denied; shows "awaiting approval" for a pending creation request).
- **Find a club:** search with debounced input, results with join policy
  hints ("Joins immediately" / "The club approves requests"), request form
  (self and wards, preferred groups, message), confirmation and "My
  requests" with withdraw.
- **Invitation landing** `/join/[token]` and code entry: club name, log in or
  sign up (Zitadel, returning to the landing page), then accept. Wrong
  account for an email invitation: explain and offer to log out.
- **Create a club:** form with country-pack defaults (time zone, locale,
  currency from the country), join policy explained; then the club page.
- **Club admin** (managers, registrars): "Join requests" list with
  approve/reject; "Invitations" with create (email, link, code; copy
  button), list, revoke; "Managers" with appoint, remove, step down, hand
  over, and the open proposal's state.
- **Handover inbox:** banner on `/` for an open proposal to me, with accept
  and decline.
- Loading, empty and error states for every list; problem types map to
  messages (`last_club_manager`, `join_not_allowed`, `invitation_invalid`,
  `invitation_email_mismatch`, `profile_incomplete`).

Mobile is out of scope (the app keeps "manage in the web app" for these
screens); invitation links open the web app.

## Email
Invitations, decisions on join requests and manager changes ("notifies all
managers", ADR 0018) need email before P1.7. Add the smallest pipeline P1.7
can build on, recorded in a new ADR:
- `MailProvider` interface with an SMTP implementation (Mailpit in
  development); a licence-allowed library or Node's own sockets.
- The API publishes domain events (IDs only); a worker outbox handler
  renders the email from IDs (recipient, locale from the account) with ICU
  message templates in `packages/i18n` (sv, en, nb) and sends it. Names in
  emails go through `PersonVisibility` (rule 4). The invitation token is
  never in an outbox payload: email invitations store an encrypted token for
  the worker (field-level encryption helpers) that is cleared after sending.
- No preferences, push or in-app notifications (P1.7).

## Privacy and security
- Personal data: name and birth date (profile completion), join request
  messages, invitation emails (normalised, never logged; deleted with the
  invitation's retention). Legal basis: membership agreement (join), the
  club's legitimate interest (invitations).
- Audit events in the same transaction for: profile completion, club
  creation and creation requests, join request created / withdrawn /
  approved / rejected, invitation created / revoked / accepted, manager
  appointed / removed / stepped down, handover proposed / accepted /
  declined / cancelled (exist), manager claimed, manager reassigned by an
  operator (with reason).
- Anti-abuse (ADR 0018): rate limits per account and per IP on search,
  join requests, invitation lookup and acceptance, club creation; per email
  domain on club creation (hosted). Invitation tokens are 32 random bytes,
  codes 8 characters; both only stored hashed and compared in constant
  time. Lookups do not reveal whether a token existed but expired.
- Email verification before any club action (the account must have
  `email_verified_at`).
- Children: a guardian can only apply for wards with `act_on_behalf`;
  children without an account never get an invitation email.
- Retention: decided join requests and used, expired or revoked invitations
  are deleted after 12 months (worker task); document in `docs/gdpr.md`.

## Protected identity
Join request lists, invitation lists (accepted by), manager lists and
emails show people through `PeopleService.summaries` + `PersonPresenter`.
A protected applicant is visible to managers and registrars (they may see
protected members) with the crossed-camera icon. Club search never lists
people. A protected person accepting a link invitation is not shown to
other acceptors or in any public count with identity.

## Locale and country packs
All new strings in sv, en and nb. Club creation defaults (time zone,
locale, currency) come from the country pack. Birth date rules
(`own_account_min_age`, consent age) come from the country pack; a person
younger than `own_account_min_age` cannot complete a profile with their own
account (explain and point to a guardian).

## Performance
- Club search: trigram index, p95 < 100 ms with 10 000 clubs (`load`
  scenario); results capped at 20 per page.
- Join request list: `join_requests_club_status_idx` (exists), keyset on
  `(created_at, id)`.
- Invitation lookup: unique index on `token_hash` (exists).
- Accepting an invitation and approving a request are single transactions
  with the club row lock; p95 < 200 ms.
- `EXPLAIN` checks in `query-plans.integration.test.ts` for the new list and
  search queries.

## Acceptance criteria
- [ ] Emma can complete her profile, find FIL, request to join, and see the
      request; a FIL registrar approves it; Emma then sees FIL in
      `/me/clubs`.
- [ ] A guardian applies for a child; the child's membership is created on
      approval; the guardian cannot apply for someone who is not their ward.
- [ ] Email, link and code invitations work end to end (Mailpit for email);
      expired, revoked and used-up invitations fail with the same 404.
- [ ] Club creation follows `CLUB_CREATION` in all three modes; with billing
      on, the new club gets its trial (P0.12).
- [ ] Appoint, remove, step down and hand over managers; the last manager
      cannot leave or be removed (service and trigger, test both).
- [ ] Chair claim and operator reassignment work only without an active
      manager / with MFA and a reason; both are audited.
- [ ] Applied memberships are migrated to join requests; no code writes
      `applied` any more.
- [ ] Rate limits on search, lookup, join requests and club creation
      (integration tests).
- [ ] Playwright: Emma's onboarding to an approved request; invitation link
      acceptance; handover proposal and acceptance.
- [ ] Tenant-isolation test for every new endpoint
- [ ] Allow/deny tests for every new policy
- [ ] Audit events for every change to personal data, roles and memberships
- [ ] Translations complete for sv and en (and nb)
- [ ] Docs updated: ADR 0018 (join requests replace applied memberships),
      new ADR for the email pipeline, `domain-model.md`, `gdpr.md`,
      `docs/api/problems.md`, `seed-data.md`

## Out of scope
- "Add child", co-guardian invitations, merges, "give own login" (P1.3).
- Waiting lists and admission from them (P1.10); joining a waiting list
  from a public page.
- Member register, member export (P1.2).
- Notification preferences, push, in-app notifications, email templates
  beyond the ones listed here (P1.7).
- Abandoned-club warnings and archiving (ADR 0018 consequence): a GitHub
  issue.
- Proof-of-work or other challenges for suspicious traffic: a GitHub issue
  (`security`).
- Mobile screens for joining, invitations and managers.
