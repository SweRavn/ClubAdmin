# P0.6 — Authentication

## Context
Read first: `CLAUDE.md`, `docs/architecture.md` (Authentication),
`docs/security.md` (Identity and sessions), `docs/seed-data.md` (DEV_AUTH),
ADR 0005, ADR 0018, ADR 0020.
What exists already: API skeleton (P0.3), core domain with `people` and
`accounts` (P0.5), Zitadel in compose (P0.2).

## Goal
People can sign up and log in with email via Zitadel; the API knows who is
calling (person, account, MFA state); the web app has a secure server-side
session; developers can log in as any person without Zitadel.

## Scope

### Zitadel configuration as code (`infra/zitadel/`)
- Idempotent script (`pnpm auth:configure`) using the Zitadel API with the
  machine user's PAT from P0.2. Creates/updates: project `clubadmin`;
  applications `web` (confidential, authorization code + PKCE, redirect
  `https://clubadmin.localhost/auth/callback`), `mobile` (native, PKCE,
  redirect `clubadmin://auth/callback`), `api` (resource / JWT audience).
- Login policy: email as login name, email verification required, passkeys
  enabled, TOTP enabled, password complexity + breached-password check,
  self-registration on/off from `USER_SIGNUP`, lockout after repeated
  failures.
- Branding: club-neutral ClubAdmin branding, Swedish and English texts.
- Output: client IDs/secrets written to `.env.local` (dev) or printed for
  operators.

### API (`apps/api/src/modules/identity`)
- Access-token validation with `jose`: issuer, audience, expiry, signature
  via cached JWKS (refresh on unknown `kid`, at most once per minute).
- **Request principal:** `{ accountId, personId, mfa: boolean, authTime,
  sessionId }`. `mfa` derived from the `amr` claim.
- **Account provisioning:** first valid login with an unknown subject creates
  `account` + `person` (given/family name from token claims, email from the
  verified email claim) via the P0.5 services. If the email already belongs to
  another account → refuse with a clear problem detail (no account merge by
  email). Email changes in Zitadel are synced on next login (and via Zitadel
  action/webhook if available).
- Linking a child's own login (ADR 0020): if the sign-up came from a
  "give own login" invitation token, link the new account to the existing
  person instead of creating one. (Invitation creation UI comes in P1.3; here
  the token verification and linking path with tests.)
- Decorators: `@Public()`, `@RequireMfa()` (403 problem detail
  `mfa_required` so clients can trigger step-up), `@RecentAuth(minutes)` for
  step-up actions.
- `GET /api/v1/me` returns the principal's person summary (through the
  presenter stub; full visibility in P0.7).
- Sessions: `GET /api/v1/me/sessions`, `DELETE /api/v1/me/sessions/:id`
  (revokes in Zitadel and in the BFF session store).

### Web BFF (`apps/web`, minimal Next.js app for now)
- Create the Next.js app (App Router, TypeScript) with only what auth needs;
  the real shell is P0.9.
- Routes: `/auth/login`, `/auth/callback`, `/auth/logout`. Authorization code
  + PKCE with `openid-client`. Tokens stored **server-side** in Valkey
  (encrypted at rest with a key from config), keyed by a random session ID.
- Cookie: `__Host-session`, `HttpOnly; Secure; SameSite=Lax; Path=/`.
- Access-token refresh in the BFF with refresh-token rotation; reuse
  detection → revoke session.
- CSRF: double-submit token for all non-GET requests from the browser to the
  BFF; the BFF forwards API calls with the bearer token (`/api/*` proxy).
- A protected test page `/me` showing the current person (name via API).

### `DEV_AUTH`
- When `DEV_AUTH=true`: the API also accepts tokens signed with a local dev
  key (`iss = clubadmin-dev`), carrying `person_id`; `mfa` can be toggled in the
  picker to test MFA-gated features.
- **Startup guard:** API and web refuse to start if `DEV_AUTH=true` and
  (`NODE_ENV != development` or `DEPLOYMENT_MODE = hosted`). Logged warning on
  every start when enabled. Tests cover the guard.
- `GET /api/v1/dev/personas` (DEV_AUTH only): lists people from the database
  with their roles (used by the persona picker in P0.9/P0.10). The web
  `/auth/login` page shows the picker when DEV_AUTH is on, plus a "real login"
  button.

## Privacy and security
- No tokens in the browser, `localStorage` or URLs.
- Token contents never logged.
- Rate limits on `/auth/*` and on account-provisioning paths.
- Security test checklist in the PR: open redirect on `returnTo`, CSRF,
  session fixation (new session ID after login), logout clears server state.

## Protected identity
`/me` and personas list go through the presenter stub, ready for P0.7.

## Locale and country packs
Zitadel login texts in sv and en; the BFF passes `ui_locales` from the
browser/user preference.

## Performance
- Token validation p95 < 1 ms with warm JWKS cache.
- Login round-trip through the BFF adds no more than one API call.

## Seed data
n/a (personas arrive in P0.8; tests create people with fixtures).

## Acceptance criteria
- [ ] `pnpm auth:configure` is idempotent and creates all apps.
- [ ] Sign up in local Zitadel → verify email in Mailpit → log in → `/me` shows the new person; DB has one account and one person.
- [ ] Signing up with an email that differs only in case from an existing one is refused.
- [ ] `@RequireMfa` endpoint returns `mfa_required` without MFA and works after enrolling a passkey/TOTP.
- [ ] Revoking a session logs out that browser on next request.
- [ ] DEV_AUTH login works; the startup guard blocks it in production mode (test).
- [ ] Playwright test: login via DEV_AUTH and via real Zitadel login form.
- [ ] `docs/architecture.md` and `docs/security.md` updated if details changed.

## Out of scope
Permissions (P0.7), mobile login (P0.10), eID/BankID, sign-up onboarding
screens (P1.1).
