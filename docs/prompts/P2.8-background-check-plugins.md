# P2.8 — Background-check plugins for Sweden and Norway; tracking screens

## Context
Read first: `CLAUDE.md`, ADR 0051 (decision 6, the background-check
contract), ADR 0047 (chat: a check where required; a club may only be
stricter), ADR 0050 (duties that need a check), P2.7 (the plugin contract
and host, background-check tables), `docs/gdpr.md` (Art. 10: criminal
records), `docs/security.md`.

What exists already (after P2.7): `packages/plugin-api` with the
`background-checks` capability, the host's storage of check metadata, test
plugins; `club.background_checks.manage`; the hooks in chat (P2.1) and
duties (P2.6) that ask whether a person has a valid check.

## Goal
Clubs in Sweden and Norway follow up their leaders' background checks in
ClubAdmin: what is required for which role or duty, who has a valid check,
who must renew and when, without storing the certificate. Chat and duties
enforce the requirement.

## Users and roles involved
Club managers and the registrar (follow-up), leaders and volunteers (the
checked), the safeguarding officer.

## User stories
- As the registrar, I see which leaders lack a valid check and remind them.
- As a coach in Sweden, I order the extract from Polisen, show it, and the
  registrar records it as verified without keeping a copy.
- As a club in Norway, the "politiattest" is requested with the
  confirmation of purpose from the club and recorded when seen.
- As a leader, I see when my check expires.

## Plugins
Each declares check types, requirements per duty category and the flows.
The exact current national rules are verified against the authorities'
pages when the prompt starts and written into the plugin with sources.

- **`plugins/se-background-check`** (Sweden): "utdrag ur
  belastningsregistret" for work with children, requested by the person
  from Polisen, shown to the club (paper or digital); at most a set age when
  shown; re-check interval set by the club (default from the federation's
  recommendation); verified by looking (and by the authority's check where
  available); never a copy, never the reference code.
- **`plugins/no-background-check`** (Norway): "politiattest" (barneomsorg)
  requested by the person with the club's confirmation of purpose, shown to
  the club; re-check per the federation's rules; same storage limits.

## Decisions
1. **Requirements** come from the plugin per duty category (regular contact
   with children, alone with children, overnight, board); the club may add
   stricter ones (more roles, shorter intervals), never weaker (ADR 0047).
2. **Proposed — mapping**: club roles, group roles and duty types are mapped to
   categories (defaults from the template roles: leaders → regular contact).
3. **Records** store type, country, issued, verified, by whom, method,
   valid until; never the document, a picture, a code or a negative outcome
   (a negative outcome closes the case and ends the role without a reason).
4. **Follow-up**: reminders before expiry (to the person and the
   registrar), a list of missing and expiring.
5. **Enforcement**: the chat rule (P2.1 rule 9) and duty eligibility
   (P2.6) ask the host; a leader without a required check keeps the role
   but cannot write to children or take such duties; the screens show why.

## Data model
Uses P2.7's tables (`background_check_records`, requests, requirements);
adds `background_check_category_mappings` (club_id, role key or duty type,
category). Club-owned, tenant RLS, history.

## API
| Method | Path | Permission | Notes |
|---|---|---|---|
| GET | `/clubs/:clubId/background-checks/overview` | `club.background_checks.manage` | Missing, expiring, valid (keyset) |
| GET/PUT | `/clubs/:clubId/background-checks/requirements` | `club.background_checks.manage` | Plugin requirements, club's stricter additions, mappings |
| POST | `/clubs/:clubId/background-checks/records` | `club.background_checks.manage` (MFA) | Record verified |
| POST | `/clubs/:clubId/background-checks/requests` | `club.background_checks.manage` | Start a request (NO flow) |
| GET | `/me/background-checks` | authenticated | My status and what is required of me |

## Permissions
`club.background_checks.manage` (from P2.7: `club_manager`, `registrar`);
reading one's own status is authenticated. Allow/deny tests; the
safeguarding officer gets read access through the template if the club
gives it.

## UI
Club → Trygghet → Registerutdrag: overview, requirements and mappings,
record dialog (no upload field), reminders. "Mitt konto": my checks and
what is required. Explanations in chat and duties when blocked.

## Privacy and security
Art. 10 data: only metadata; access logged; no negative outcomes.
**Proposed:** records deleted when the person leaves all roles that need
them (plus a short period set in the registry). DPIA note in `gdpr.md`.

## Protected identity
Overview lists through `PersonPresenter`.

## Locale and country packs
Plugins carry their texts in sv, en, nb; the UI translated.

## Performance
Overview from the club's leaders with an index on (club, valid_until);
budgets.

## Seed data
IKN: three leaders with valid checks, one expiring, one missing (blocked
from writing to children in chat); a Norwegian demo club with the NO plugin.

## Acceptance criteria
- [ ] SE and NO plugins pass the conformance suite of P2.7
- [ ] Requirements, club stricter additions, mappings
- [ ] Records without documents, codes or negative outcomes
- [ ] Reminders; enforcement in chat and duties
- [ ] Tenant isolation, allow/deny, matrix rows, budgets, audit, history
- [ ] Translations sv, en, nb; docs (`gdpr.md`, ADR 0051 "As implemented",
      `docs/plugins.md`)

## Out of scope
- Automatic verification against the authorities' APIs where none is
  open to clubs; other countries (third-party plugins).
- Federation feeds (e.g. France) as real plugins.
