# P2.4 — Documents I: file archive, audiences, documents attached to notices

## Context
Read first: `CLAUDE.md`, ADR 0049 (decisions 1A, 2, 4b, 6–10), ADR 0011
(file storage), ADR 0012 and P0.12 (entitlements), ADR 0022, ADR 0040,
`docs/security.md` (file handling), `docs/gdpr.md`.

What exists already:

- Object storage client `@clubadmin/server-kit/object-storage` (used by
  imports and exports, pre-signed URLs); ClamAV in `pnpm dev:services
  --full`, not yet used in code.
- Events have audiences with audience groups; activities have call-ups;
  notifications (P1.7); entitlements service.
- No documents tables.

## Goal
Clubs and groups keep their files in ClubAdmin: folders, versions, and an
audience that decides who sees what. Notices of activities and events carry
documents as links. "Mina dokument" shows what is new across clubs and
groups. This is the base the governing documents and meetings of P2.5 build
on.

## Users and roles involved
Club managers, the secretary, group leaders (managers of files); members,
guardians (readers); protected people.

## User stories
- As a coach, I create a folder "Matchschema" in my team and upload the
  spring schedule; players and guardians of the team see it.
- As the secretary, I put the club's policy documents in a folder for the
  whole club and the traffic policy as public.
- As a coach, I attach the cup's information to the cup's notice by
  picking it or uploading it; the invitees get a link.
- As a member, "Mina dokument" shows what is new in my groups and club.
- As an uploader, I add a new version of a file; the old one stays.

## Decisions (ADR 0049)
1. Folders at club or group level; group leaders create their group's
   folders. Files have versions (each kept and downloadable).
2. **Audience** on a folder (inherited) or a file (narrower or wider):
   whole club (members and their guardians), a group (optionally some roles
   in it), a club role, public. The audience model is shared (announcements,
   P2.2, use it too). An "access group" is an ordinary group of kind
   `other`.
3. **Attached to notices**: an activity's or event's notice lists documents
   picked from ClubAdmin or uploaded (stored in the group's or club's
   "Kallelser" folder through the same scanning). Notices send links only;
   being invited adds the notice's recipients to the document's audience
   while it is attached. The creator sees what is attached and to whom it
   is thereby shown.
4. **Files**: type allow list, size limits, ClamAV before visible, served
   from a separate domain as attachments with pre-signed URLs.
5. **Storage limits**: the operator's limit per installation or plan
   (entitlements); the club's own within it, divisible per group. An upload
   over the limit is refused with a clear message.
6. Kept until deleted; deleting a folder deletes its files after a
   confirmation; deletions are audited. Part of the club's full export.
7. Push for new documents only when the uploader asks (no push per file by
   default).

## Data model
Club-owned, tenant RLS, history, `updated_at`, person references declared.

- `audiences` + `audience_entries` (kind `club` | `group` | `group_roles` |
  `club_role` | `public`, group_id, role keys), shared by documents and
  announcements.
- `document_folders` (club_id, group_id nullable, parent_id, name,
  audience_id, created_by).
- `documents` (club_id, folder_id, kind `file` | `governing` (P2.5), name,
  audience_id nullable = folder's, current_version_id, archived_at).
- `document_versions` (document_id, object key, size, content type, sha256,
  scan status `pending` | `clean` | `infected`, uploaded_by, created_at).
- `notice_attachments` (activity_id or event_id, document_id, attached_by).
- `document_views` (person_id, last_seen_at per club/group) for "new since".
- `storage_quotas` (club, group, limit; usage computed from versions).

## API
| Method | Path | Permission | Notes |
|---|---|---|---|
| GET | `/me/documents` | authenticated | "Mina dokument": new and recent, keyset |
| GET | `/clubs/:clubId/folders/:id` | audience | Folder content |
| POST/PATCH/DELETE | `/clubs/:clubId/folders[/:id]` | `club.documents.manage` / `group.documents.manage` | Create, rename, audience, delete |
| POST | `/clubs/:clubId/documents/uploads` | as folder | Pre-signed upload; then confirm → scan |
| GET | `/clubs/:clubId/documents/:id[/versions/:v]/download` | audience | Pre-signed download after a clean scan |
| PATCH/DELETE | `/clubs/:clubId/documents/:id` | as folder | Rename, move, audience, delete |
| PUT | `/clubs/:clubId/activities/:id/attachments` | can edit the activity | Pick or upload; same for events |
| GET/PUT | `/clubs/:clubId/storage` | `club.documents.manage` | Usage, club and group limits |
| GET | `/public/clubs/:slug/documents` | public | Public documents |

## Permissions
| Permission | Scope | Allows | Default |
|---|---|---|---|
| `club.documents.manage` | club | The club's folders and files, all audiences, storage limits | `club_manager`, `secretary` |
| `group.documents.manage` | group | The group's folders and files | `head_coach`, `assistant_coach`, `team_manager`; owners |

Reading is decided by the audience, with allow/deny tests for each entry
kind, guardians, notice attachments (and their end when detached).

## UI
- A "Dokument" tab for the club and each group: folders, files, versions,
  upload with progress and scan state, audience editor with a preview of
  who sees it.
- "Mina dokument" (app and web).
- Activity and event forms: attachments (pick or upload) and the list of
  who they are thereby shown to.
- Club settings: storage usage and limits.

## Privacy and security
Files can contain personal data; the uploader is responsible and the help
text says so. Scanning before visibility; downloads logged in the audit
for documents with an audience narrower than the club. No file contents in
logs. Erasure removes the person as uploader (anonymised), not the files.

## Protected identity
Uploaders and "shown to" lists through `PersonPresenter`.

## Locale and country packs
sv, en, nb; no country rules.

## Performance
Folder listing keyset by name; "Mina dokument" from the person's groups
with an index on (group, created_at); audience checks in SQL, not per row in
code; budgets for each endpoint.

## Seed data
IKN: club folder "Policyer" (whole club) with two files and one public;
F2015's "Matchschema" with a file in two versions; a cup notice with an
attached document.

## Acceptance criteria
- [ ] Folders, files, versions, audiences, scanning, limits
- [ ] Notice attachments as links; audience follows the attachment
- [ ] "Mina dokument" and group tabs on web and app
- [ ] Tenant isolation, allow/deny, matrix rows, budgets, audit, history
- [ ] Included in the club's full export
- [ ] Translations sv, en, nb; docs (`domain-model.md`, `security.md`,
      ADR 0049 "As implemented")

## Out of scope
- Governing documents, meetings, signing (P2.5).
- Files in chat (later, same storage).
- Public pages (Phase 3; only the public listing endpoint here).
