# P0.10 — Mobile shell (iOS and Android) and per-account rate limits

## Context
Read first: `CLAUDE.md` (mobile licence rule), `docs/architecture.md`
(Authentication, Web app, Locale), `docs/performance.md` (Mobile),
`docs/security.md` (rate limits), `docs/licensing.md` (Mobile app stores),
ADR 0005, ADR 0008, ADR 0022, ADR 0024, ADR 0027, issues
[#7](https://github.com/SweRavn/ClubAdmin/issues/7) and
[#11](https://github.com/SweRavn/ClubAdmin/issues/11).

What exists already:
- **Zitadel** app `mobile` (native, PKCE, no secret) in
  `infra/zitadel/clubadmin.json` with redirect `clubadmin://auth/callback` and
  post-logout `clubadmin://auth/logout`; access and ID tokens 10 min, refresh
  tokens 30 days idle / 90 days at most.
- **API**: `AuthGuard` takes `Authorization: Bearer` plus the ID token in
  `X-Id-Token` (bound by `at_hash`, ADR 0024) and provisions unknown subjects
  (in-memory limit of 10 per IP and minute, `IdentityService.limitProvisioning`,
  #7). `api.clubadmin.localhost` serves the API directly for clients with
  their own tokens. Read endpoints used by the web shell: `/me` (with
  `preferences`), `PATCH /me/preferences`, `/me/clubs` (club language, time
  zone, club-level permissions), `/me/groups`, `/me/wards`, `/me/sessions`,
  `/clubs/:id`, `/clubs/:id/groups`, `/groups/:id`, `/groups/:id/members`,
  `/people/:id`, `/meta/source`, `/meta/version`. `X-On-Behalf-Of` for
  guardians (not on `/me`, `/me/wards|sessions|preferences|security`, `meta`,
  `dev`; see `onBehalfApplies` in `apps/web/src/server/api.ts`).
- **DEV_AUTH**: `GET /api/v1/dev/personas`; the web BFF signs HS256 tokens with
  `DEV_AUTH_KEY` (`apps/web/src/server/dev-tokens.ts`). The key must never be
  in the app.
- **Sessions**: `/me/sessions` lists the BFF's browser sessions from Valkey
  and revoking ends the Zitadel session (`sessions.service.ts`). Mobile logins
  are not listed today.
- **Rate limit**: one global `@fastify/rate-limit` per client IP
  (`RATE_LIMIT_MAX`, default 300/min, Valkey-backed, fail open); the BFF
  forwards the browser's `X-Forwarded-For`; development raises the limit to
  3000 (#11). BFF `/auth/*`: 30 per IP and minute.
- **i18n**: `@clubadmin/i18n` holds nested ICU catalogues (sv, en complete;
  nb falls back) and `localeOf`/`negotiateLocale`; the web reads them through
  next-intl on the server. Catalogues are imported with JSON import
  attributes.
- **Web shell** (P0.9) as the reference for screens, locale and time-zone
  chains, protected identity (`PersonName`, `ProtectedBadge`, `personLabel` in
  `packages/ui`, web-only) and the ESLint rules against JSX literals and name
  fields.
- `apps/mobile` holds only a README; `pnpm licenses:check --mobile` already
  checks `@clubadmin/mobile`'s production tree once it exists.

## Goal
An Expo app for iOS and Android that logs in securely, shows my clubs, groups
and members with exactly the same visibility as the web, opens instantly from
an encrypted per-account cache (also offline), and passes the stricter mobile
licence check, ready for app-store builds later. Because the app calls the API
directly from many devices behind shared addresses (mobile carrier NAT, club
houses), the API's rate limits move from per IP to per account first (#11,
#7).

## Scope

### 1. Rate limits per account and per club (closes #11 and #7)
Do this first; the mobile app depends on it.
- **Unauthenticated requests**: per client IP, as today (`RATE_LIMIT_MAX`,
  default 300/min).
- **Authenticated requests**: per account (`RATE_LIMIT_ACCOUNT_MAX`), counted
  after the token is verified (the principal's `accountId`; the on-behalf-of
  ward does not get its own budget). Size the default from the real fan-out:
  a web page view makes about five API calls, and a mobile screen a few more
  on cold start. Measure both and write the numbers and the chosen limit in
  `docs/security.md`.
- **Per club for bulk reads**: an `@Endpoint` option marks list endpoints
  that page through a club's people (today `/groups/:id/members`, and later
  exports); they also count against a per-club budget
  (`RATE_LIMIT_CLUB_BULK_MAX`), so one club's scraping cannot cost every
  member's budget and one account cannot read a club wholesale.
- **Per-IP backstop**: authenticated requests still count against a much
  higher per-IP limit (`RATE_LIMIT_IP_BACKSTOP`), which catches token
  stuffing from one address without punishing a shared NAT.
- All counters live in Valkey (shared across API instances), with an
  in-memory fallback when Valkey is not configured. Answer `429` problem
  details with `Retry-After`. Fail open when Valkey is unreachable, except
  where noted below.
- **First-login provisioning (#7)**: the 10-per-IP-and-minute limit moves to
  the same Valkey limiter (`ratelimit:provisioning:<ip>`, 60 s window); the
  in-memory map goes away. Creating an account **fails closed** when Valkey
  is configured but unreachable (`503`, documented in `docs/security.md`).
  Integration test with two API instances sharing one Valkey.
- The web BFF keeps forwarding `X-Forwarded-For`. The development override
  `RATE_LIMIT_MAX=3000` is removed from `.env.example` and the devtools env
  template if the end-to-end suites pass with the defaults; otherwise keep
  only what is needed, and say why in the comment.
- Integration tests: per-account limit independent of IP (two accounts on one
  IP each get their own budget; one account from two IPs shares one budget),
  per-club bulk budget, backstop, unauthenticated per-IP limit, `Retry-After`.
- Benchmark: the request pipeline benchmark (`pnpm --filter @clubadmin/api
  bench`) stays within the P0.3 baseline plus the cost of one Valkey round
  trip; record the result in `docs/performance.md`.

### 2. API additions for mobile
- **Dev tokens**: `POST /api/v1/dev/tokens` (registered only with DEV_AUTH,
  like `/dev/personas`; `{ public: true }`; body `{ personId, mfa }`) returns
  an access token and ID token signed by the API with `DEV_AUTH_KEY` (same
  claims as the web's `mintDevToken`; move that function to a shared
  server-side place so web and API use one implementation). No refresh
  token: the app asks for new tokens when they expire. Rate-limited per IP
  like other unauthenticated calls.
- **Mobile sessions in `/me/sessions`**: the first authenticated request of a
  new Zitadel session (`sid`) from the `mobile` client (`azp`) registers it in
  the person's session index (platform, app version and device model from
  request headers, never a device identifier), updating `lastSeenAt` at most
  once per few minutes. Revoking a mobile session ends the Zitadel session.
  Verify (test) that this makes the app's refresh token fail; the access token
  may live out its 10 minutes (document this window in `docs/security.md`).
- `onBehalfApplies` moves from `apps/web` to `packages/api-client` so web and
  mobile share one rule.

### 3. Project
- Expo (current SDK, exact versions old enough for `minimumReleaseAge`) in
  `apps/mobile` as `@clubadmin/mobile`, Expo Router, TypeScript strict, Hermes.
  React Native's React version may differ from the web's: use a separate pnpm
  catalog entry if so, and say why in `pnpm-workspace.yaml`.
- Metro in the pnpm workspace: workspace packages are TypeScript source with
  `.ts` import extensions and JSON import attributes (`@clubadmin/i18n`);
  configure Metro/Babel for both, without a build step for the packages.
- Uses `packages/api-client`, `packages/shared`, `packages/i18n`. Nothing from
  `packages/ui` or other web-only packages (dependency-cruiser rule).
- App variants by `APP_VARIANT` (`development`, `preview`, `production`):
  bundle IDs, app names and URL schemes differ per variant
  (`clubadmin-dev://` and so on) so variants can be installed side by side;
  every redirect URI is listed in `infra/zitadel/clubadmin.json`.
- API base URL and issuer from app config (`app.config.ts`, from environment
  at build time), defaulting to the local Caddy domains in development.
- **`pnpm licenses:check --mobile` must pass**: no GPL/LGPL/AGPL in the
  bundle. Every new dependency goes in the table in `docs/licensing.md`.
- ESLint: the JSX literal-strings rule and the person-name rule
  (`clubadmin/person-names-in-presenters` with `fields`) apply to
  `apps/mobile`; name fields only in the mobile `PersonName` component.

### 4. Authentication
- Authorization code + PKCE through the system browser
  (`expo-auth-session` / `expo-web-browser`), Zitadel `mobile` app, scopes
  `openid profile email offline_access` plus the project audience scope used
  by the web.
- Refresh token in `expo-secure-store` (Keychain/Keystore, only available
  after first unlock); access and ID tokens in memory only. Refresh before
  expiry and on `401`, one refresh at a time (concurrent requests wait);
  rotation; a rejected refresh logs the user out cleanly.
- Every API call sends `Authorization` and `X-Id-Token`, and `X-On-Behalf-Of`
  where `onBehalfApplies` says so.
- Logout: revoke the refresh token at Zitadel, end the Zitadel session
  (`end_session` with `clubadmin://auth/logout`), wipe tokens, cache and the
  cache key.
- Development builds with DEV_AUTH: persona picker screen (grouped by club,
  with the descriptions, tags and MFA toggle as on the web) using
  `/dev/personas` and `/dev/tokens`. The screen is compiled out of preview
  and production builds (build-time constant, checked in a test of the
  release bundle), and the API refuses DEV_AUTH outside development anyway.
- Optional biometric unlock (`expo-local-authentication`) when reopening the
  app, off by default, a setting.
- Handles `429` by honouring `Retry-After` (TanStack Query retry), and
  `403 mfa-required` / `reauthentication-required` by explaining that the
  action needs the web for now (step-up on mobile comes later).

### 5. Screens
- Login, Home (my clubs, my groups, my children's groups, onboarding
  placeholder for people without clubs), club switcher (remembers the last
  club per person), club overview, groups tree, group (owners, leaders,
  members, paginated with `FlashList` or `FlatList`), person profile
  (fields as the API returns them), Settings (language, time zone, theme,
  sessions with revoke, biometric unlock, log out), About (version, the
  **Source code** link from `/meta/source`, and the third-party licence list
  generated at build time).
- "Viewing as" child switcher for guardians, clearly shown, as on the web.
- Mobile UI components of our own: `PersonName` (accepts only
  `PersonSummary`), `ProtectedBadge` (the crossed-camera icon with an
  accessible label and the same explanation as the web tooltip), `RoleBadge`,
  `EmptyState`, `DateTime`. Move the pure display logic (`personLabel`, role
  labels) out of `packages/ui` into a package both apps can use.
- Loading, empty, offline and error states (problem-details aware: 404 page
  for cross-club links, 403 for missing permissions).

### 6. i18n and locale
- Messages from `@clubadmin/i18n`; app-specific keys in a `mobile`
  namespace; sv and en complete, nb may fall back (the existing catalogue
  test covers the new keys).
- Use `use-intl` (MIT, next-intl's framework-agnostic core) so web and mobile
  share message syntax and formatting; check what Hermes's `Intl` supports
  (plural rules, time zones, relative time) on the oldest supported OS
  versions and add `@formatjs` polyfills only where needed.
- Locale: before login the device locale (`expo-localization`) →
  `en`; after login user preference → current club's `defaultLocale` →
  device locale → `en`. Time zone: user preference → club → device. Times
  in the club's time zone, showing the viewer's zone when different (as on
  the web).

### 7. Data and offline
- TanStack Query persisted to MMKV (`react-native-mmkv`): cached screens
  render immediately on cold start, then refresh in the background.
- One MMKV instance **per account**, **encrypted** with a random key kept in
  the secure store; switching account or logging out deletes the instance
  and its key. Tokens are never in MMKV or AsyncStorage.
- The cache holds names of protected people for viewers allowed to see them,
  so it is never written to logs, crash reports or backups (exclude it from
  iCloud/Android backup).
- Network-status banner; read-only offline mode (writes and the offline
  outbox come in P1.5). Cached data older than a configurable age is shown
  with its age.

### 8. Local development and CI
- `pnpm dev` does not start Metro; `pnpm --filter @clubadmin/mobile start`
  does. Development builds reach the local API through Caddy:
  - iOS simulator: shares the host's network; `pnpm dev:trust-ca` adds
    Caddy's CA to booted simulators (`xcrun simctl keychain booted
    add-root-cert`), or prints the command.
  - Android emulator: reach the host through `adb reverse` (or `10.0.2.2`
    with the right SNI; pick one and document it) and trust Caddy's CA only
    in development builds (network security config generated from
    `.local/caddy-root.crt`, never in preview or production builds).
- Unit tests with `jest-expo` and React Native Testing Library (token
  refresh and logout, cache per account and wipe, `onBehalfApplies`, locale
  chain, `PersonName` and `ProtectedBadge`).
- End-to-end with Maestro (Apache-2.0) on the Android emulator in CI: log in
  as a persona; switch club; open a group; protected identity (Liam does not
  see Nadia in IKN F2015, Erik sees her with the icon); language (Lars sees
  Norwegian); viewing as (Anna → Elsa); offline cold start with cached Home;
  logout wipes data. One flow logs in through real Zitadel (PKCE in a Custom
  Tab) with the Zitadel e2e test user from P0.6.
- CI: typecheck, lint, unit tests, `licenses:check --mobile`, an Android
  debug build (`expo prebuild` + Gradle) and the Maestro flows on Linux
  runners (KVM), as a job of its own next to the web jobs. An iOS simulator
  build on a macOS runner runs manually (`workflow_dispatch`).
- Accessibility: dynamic type, screen-reader labels on every control and the
  protected icon, contrast in light and dark themes, touch targets ≥ 44 pt.

## Privacy and security
- No personal data in logs, crash reports or analytics (there are none);
  log IDs only.
- Android `FLAG_SECURE` on screens that show protected people to privileged
  viewers; iOS hides app content in the app switcher on those screens.
- Deep links: only the variant's scheme, only known paths, IDs validated as
  UUIDs; universal links come with app-store identities (out of scope).
- The release build contains no DEV_AUTH code path, no development CA and
  no API URL other than the configured one.

## Protected identity
Visibility comes from the API; the app only shows `PersonSummary` through its
`PersonName`. Maestro checks the same personas as the web (Liam, Erik,
Samira, Emma → 404 on the group link).

## Performance
- Cold start to cached Home < 2 s on a mid-range Android profile, measured in
  a release build on the CI emulator and documented in
  `docs/performance.md`.
- Home makes no request waterfall: `/me`, `/me/clubs`, `/me/groups` and
  `/me/wards` in parallel.
- JS bundle (Hermes bytecode) size reported in CI with a budget set from the
  first measurement (recorded with the reasoning, as ADR 0027 did for web).

## Seed data
Uses the P0.8 personas; no new data.
