# P0.2 — Local development environment

## Context
Read first: `CLAUDE.md`, `docs/architecture.md`, `docs/hosting-and-billing.md`,
ADR 0005, ADR 0010, ADR 0011.
What exists already: monorepo skeleton and CI (P0.1).

## Goal
`pnpm dev` starts every backing service locally with one command, on Linux,
macOS and Windows (WSL2), so later packages can run against real Postgres,
Valkey, Zitadel and object storage. The same compose files are the basis for
self-hosting later.

## Scope

### Compose files (`infra/docker/`)
- `compose.yml`: services shared by dev and self-hosting.
- `compose.dev.yml`: dev overrides (ports exposed on localhost, dev
  credentials, volumes).
- Services:
  | Service | Image | Notes |
  |---|---|---|
  | `postgres` | official PostgreSQL 18 | Init script creates databases `clubadmin` and `zitadel` (roles come in P0.4). `shared_preload_libraries=pg_stat_statements`. Healthcheck. |
  | `valkey` | official Valkey | No persistence needed in dev. |
  | `zitadel` | official Zitadel (v3+) | Uses the `zitadel` database. First-instance setup creates an admin user and a machine user with a PAT written to a mounted volume, for P0.6's config-as-code. |
  | `garage` | official Garage | Single-node layout, init job that creates buckets `clubadmin-files` and `clubadmin-backups` and an access key. |
  | `mailpit` | Mailpit | SMTP on 1025, web UI on 8025, so every email can be inspected. |
  | `caddy` | official Caddy | `tls internal`; routes `https://clubadmin.localhost` → web (3000), `/api` → api (4000), `https://auth.clubadmin.localhost` → Zitadel. Real HTTPS locally so `Secure` cookies behave as in production. |
  | `clamav` | official ClamAV | In a `full` profile only (slow to start), used from Phase 2. |
- Named volumes for data; `pnpm dev:clean` removes them.
- Pin images by version **and** digest in `compose.yml`; Renovate updates them.

### Scripts (root `package.json`)
- `pnpm dev`: `docker compose up -d --wait` for services, then `turbo dev` for
  apps (apps are placeholders for now; they just log that they started).
- `pnpm dev:services` (services only), `pnpm dev:down`, `pnpm dev:logs`,
  `pnpm dev:clean`, `pnpm dev:doctor` (checks Docker, ports, Node version,
  trust of Caddy's local CA, prints fixes).
- `pnpm dev:trust-ca`: installs Caddy's local root CA in the OS trust store
  (documented manual steps for each OS as fallback).

### Configuration
- `.env.example` extended with all service URLs and dev credentials (dummy,
  clearly dev-only). Apps load `.env` then `.env.local` (git-ignored).
- `infra/docker/README.md`: what each service does, ports, how to reset,
  troubleshooting.

### Docs
- `docs/development.md`: prerequisites (Docker, Node via Corepack), first run,
  daily workflow, where to see emails (Mailpit), how to reset.

## Privacy and security
- Dev credentials are random per install where possible (`pnpm dev` generates
  `.env.local` secrets on first run); never reused in production.
- Nothing listens on non-localhost interfaces by default.

## Acceptance criteria
- [ ] `pnpm dev` on a clean machine brings up all services healthy; `pnpm dev:doctor` reports OK.
- [ ] `https://clubadmin.localhost` shows a placeholder via Caddy with a trusted certificate after `pnpm dev:trust-ca`.
- [ ] Zitadel console reachable at `https://auth.clubadmin.localhost`; machine-user PAT present in the mounted volume.
- [ ] Sending a test email to `localhost:1025` shows up in Mailpit.
- [ ] Garage buckets exist and are writable with the generated key.
- [ ] CI job builds and starts the compose stack (without ClamAV) and checks health.
- [ ] `docs/development.md` written.

## Out of scope
Production/self-hosting hardening (later), database roles and migrations
(P0.4), Zitadel project/app configuration (P0.6), backups (P0.11).
