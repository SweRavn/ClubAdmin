# P1.6b — Clean-up after hands-on testing: forms, groups, places, club settings, answers

## Context
Read first: `CLAUDE.md`, ADR 0019 (groups), ADR 0022 (protected identity),
ADR 0029 (the API only grows), ADR 0034 (activities and locations), ADR 0035
(responses and attendance), ADR 0038 (events), `docs/domain-model.md`,
`docs/development.md`, `docs/seed-data.md`, and the draft
`P1.10-groups-admin-and-waiting-lists.md` (this prompt takes its basic group
administration and the applicant's read-only view of waiting lists; P1.10
keeps owners, hierarchy moves, admission and running the waiting list).

The maintainer tested P1.1–P1.6 by hand with the demo personas. This prompt
fixes what was wrong or missing; it adds no new feature area. Findings, with
what the code does today:

1. **Event form demands too much.** `CreateEventSchema` requires `title`,
   `startsAt`, `endsAt` and `registrationClosesAt`; the web form marks start,
   end and sign-up deadline as required (`components/event-fields.tsx`).
2. **Member lists sort by family name.** Group rosters and the member
   register order by `sort_name = lower(family_name) || ' ' ||
   lower(given_name)` (`memberships.repository.ts`, `packages/db/src/register.ts`,
   migrations 0003 and 0008).
3. **Groups cannot be created, edited, renamed or removed** (items 3, 4, 17
   and 18 of the test notes). `GroupsService.createGroup`, `updateGroup`
   and `archiveGroup` exist without endpoints; `group.update` has a policy
   but guards nothing; the web pages are read-only.
4. **Sessions with an event are three fixed rows** of the four activity
   kinds (`clubs/[clubId]/events/new/page.tsx`); there is no way to add
   more or to say what "other" is.
5. **Sign-up questions** are three empty rows on the new-event form and one
   on the edit form ("add a question" saves and returns).
6. **Only club managers manage places** (`club.locations.manage`); leaders
   cannot add the hall they train in. `locations` has no creator column.
7. **No warning when an event ends before it starts.** The server answers
   `invalid_input` and the form comes back empty.
8. **A new event "disappeared".** It was saved as a draft (the "publish now"
   box is off by default) and drafts show only on `/clubs/:id/events`,
   reached through a small link next to "Groups" on the club page, and on
   the group page; never on "My schedule" or the start page.
9. **Adding a member from a paper form asks for a second factor.** The
   policy of `club.members.add` asks club managers who are not registrars
   for MFA. With DEV_AUTH the login picker has an "MFA" box, but the error
   does not say so.
10. **Joining with a code before having an account** has no entry point: the
    code field is only on the start page's onboarding panel, after sign-up
    and a completed profile, and not shown to people who already belong to
    a club. `/join/[token]` takes link tokens only.
11. **No demo user can log in with email and password.**
    `docs/seed-data.md` mentions `pnpm dev:idp-sync` (personas in Zitadel
    with password `demo-password-123`), but the script does not exist.
12. **People on a waiting list do not see it.** `group_waitlist_entries` is
    read by nothing; a pending join request shows only on the start page's
    "in progress" panel (e.g. Henrik for Viktor Malm).
13. **Changing an answer and its note did not stick** (Erik for Maja,
    "Innebandyträning"). The API is correct; the form is not: the note is
    one `<input>` in a form with two submit buttons, so Enter submits
    "attending"; the note is never pre-filled, so answering again without
    it deletes the old note; leaders may also try the read-only response
    list or the attendance sheet, which opens an hour before the start.
14. **Preferences: an empty time zone gives "Unknown time zone".** The API
    accepts `timeZone: null` ("the club's"), and the web route sends null
    for an empty field, but every failed save is shown as
    `preferences.invalidTimeZone`, whatever the real problem was.
15. **The club's time zone and contact details cannot be set.**
    `UpdateClubSettingsSchema` and `ClubsService.updateSettings` exist
    without an endpoint or page; `clubs` has no email or phone columns.
16. **Leaders cannot answer for their members.** `activity.respond` allows
    only the person and guardians with `sign_up`.

## Goal
After this prompt the maintainer can run a club's season in the web app
without workarounds: create and edit groups and places, set the club's time
zone and contact details, create events with as little or as much detail as
needed, answer for players as a leader, and see where a family stands in a
queue. Lists read naturally (given name first) and errors say what is wrong.

## Users and roles involved
Club managers (groups, club settings, all places), group owners and leaders
who manage a group's activities (their groups' settings, places, answering
for their members), registrars (members from paper forms), members and
guardians (answers, preferences, queue status, joining with a code), people
without an account (joining with a code).

## User stories
- As an organiser, I want to save an event with only its name and start
  date, and fill in the rest later.
- As a leader, I want rosters and lists in given-name order, as the team
  calls each other.
- As a club manager, I want to create, rename and edit groups (name, kind,
  sport, birth years, gender category, capacity, parent group) and remove
  one that was created by mistake or archive one that has ended.
- As an organiser, I want to add as many sessions to an event as it has, and
  say what a session is when it is none of the given kinds.
- As an organiser, I want to add as many questions as the form needs without
  saving in between.
- As a leader, I want to add the places my group uses and fix my own
  entries, without being able to change places others added.
- As an organiser, I want to be told at once when the end is before the
  start, and keep what I typed.
- As an organiser, I want to find my drafts again.
- As a registrar or club manager in development, I want to know how to log
  in with a second factor when an action needs one.
- As a parent with an invitation code, I want to type it before I have an
  account and be taken through sign-up to the club.
- As the maintainer, I want demo users that log in with email and password
  through Zitadel.
- As a parent, I want to see that my child is on a team's waiting list, and
  where.
- As a parent, I want to change my child's answer and note reliably.
- As a user, I want to pick my time zone from a list, or "the club's time
  zone".
- As a club manager, I want to set the club's time zone, email, postal
  address, organisation number and several phone numbers.
- As a leader, I want to answer "coming" / "not coming" for my players in
  the answers table.

## Data model
Forward-only, expand-only migrations (CLAUDE.md rules 3 and 13); every new
table with tenant RLS, `updated_at`, record history.
- `locations.created_by_person_id` (nullable; existing rows null = created
  by a club manager) with an index; declared in
  `activities.references.ts`.
- `clubs.email` (nullable text, validated as an email; the club's contact
  address, not a login) and `club_phone_numbers` (club-owned: `label`, e.g.
  "Kansli", `number`, `sort_order`; at most 10 per club). Postal address,
  organisation number and time zone already exist.
- Sort order (item 2): a `sort_given_name` expression
  (`lower(given_name) || ' ' || lower(family_name)`) next to `sort_name` in
  the views/functions that feed the roster and the register, with the
  indexes they need; given name first becomes the default everywhere names
  are listed (rosters, register, answers, attendance, registrations, family
  lists). The register keeps a "family name" sort option.
- `activities.kind_label` (nullable, max 60): what an `other` activity is
  ("Cup", "Lunch"). Shown instead of "Other" wherever the kind is shown.
- `events.ends_at` stays required in the table; the service fills it
  (below). No new columns for events.

## API
Under `/api/v1`; writes refused for clubs that are not active (ADR 0031).
Only additions (ADR 0029).

| Method | Path | Permission | Notes |
|---|---|---|---|
| POST | `/clubs/:clubId/groups` | `club.groups.create` (new) | Club managers; owners of a parent group create children of it (the service checks the parent). `CreateGroupSchema` as P1.10 |
| PATCH | `/groups/:groupId` | `group.update` | Name, kind, sport, birth years, gender category, capacity, admission mode, parent (no cycles, same club). Audited |
| POST | `/groups/:groupId/archive` / `/restore` | `group.update` | As P1.10: refused with unarchived children (`group_has_children`); restore club managers only |
| DELETE | `/groups/:groupId` | `group.update` | Only a group that never had memberships, activities, events or waiting-list entries (`group_in_use`: archive it instead). Hard delete, audited |
| PATCH | `/clubs/:clubId/settings` | `club.settings.update` | Time zone (from `Intl.supportedValuesOf('timeZone')`), email, postal address, organisation number (country-pack validation for `se`), default locale |
| PUT | `/clubs/:clubId/phone-numbers` | `club.settings.update` | The whole list `{ label, number }[]` (create, edit, remove and reorder in one call) |
| POST | `/clubs/:clubId/locations` | `club.locations.create` (new) | Club managers and those who manage any group's activities; records the creator |
| PATCH | `/clubs/:clubId/locations/:locationId` | `club.locations.manage` (changed) | Club managers, or the location's creator (the service checks; others `forbidden`) |
| PUT | `/activities/:activityId/responses/:personId` | `activity.respond` (widened) | Also those who lead one of the activity's groups, for its participants; `respondedBy` is the leader; the deadline does not bind leaders. Audited as `activity.response.set_by_leader` |
| GET | `/me/waitlists` | own data | From P1.10, read-only here: my and my wards' open entries (group, club, status, position, number waiting) and pending join requests with their preferred group |
| GET | `/invitations/lookup?code=` | public | Exists; used by the new `/join` page |

Events (changed): `CreateEventSchema` requires only `title` and `startsAt`.
`endsAt` defaults to the end of the start day in the club's time zone (or
two hours after a start with a time); `registrationClosesAt` defaults to
`startsAt`. A specific problem code `event_period_invalid` (end not after
start, sign-up closing after the end) replaces `invalid_input` for these
cases. `EventActivityInputSchema` and the activity schemas accept
`kindLabel`. The number of sessions with an event stays capped at
`EVENT_ACTIVITIES_MAX` (20), questions at 20.

Preferences: `PATCH /me/preferences` answers each invalid field with its own
code (`invalid_time_zone`, `invalid_locale`, …); `timeZone: null` is "the
club's time zone".

## Permissions
- `club.groups.create` (club): club managers; owners of a group (for child
  groups, checked by the service). Allow: manager, section owner; deny:
  coach, member, outsider (404).
- `group.update` (now guarding endpoints): club managers, owners of the
  group or a parent group. Deny: coach, member.
- `club.locations.create` (club): club managers and anyone who manages a
  group's activities (`managesAnyGroupActivities`). Deny: plain members,
  guardians.
- `club.locations.manage` (location): club managers, or the creator.
  Deny: another coach.
- `activity.respond`: add leaders of one of the activity's groups
  (`canLeadGroupActivities`); the controller allows them any participant on
  the roster. Deny: physio, members for others.
- `club.settings.update`: unchanged (club managers with MFA).
- Matrix entries for every new or changed endpoint, tenant isolation (404
  for club B).

## UI
Web unless noted; all strings in sv, en and nb.
- **Event form** (`event-fields.tsx`, new and edit): only name and start
  date required (time optional); end, sign-up opening and deadline,
  cancellation deadline, capacity optional with the defaults shown as hints.
  Client-side check that the end is after the start and the deadline not
  after the end (a message next to the field, the button disabled), and the
  server's `event_period_invalid` shown next to the end field. A failed save
  keeps every value typed (the action returns the form values, or the form
  posts to itself).
- **Sessions and questions:** a list with "Add session" / "Add question"
  that adds a row in the browser (a small client component), up to the
  limits; without JavaScript, "Add" saves the draft and returns with one
  more row (as the edit form does now). Rows can be removed. The session
  kind is a select of the activity kinds; "Other" shows a "What is it?"
  text field (`kindLabel`).
- **Drafts:** "Publish now" is on by default for new events; the event list
  gets its own entry in the club menu ("Events"), and organisers see their
  drafts there and on the group page under "Drafts" with a badge. After
  saving a draft the notice says where to find it.
- **Groups:** on the club's groups page "New group" (name, kind, parent,
  optional details); on a group page "Edit" (all fields above), "Archive" /
  "Restore", and "Delete" for unused groups (with a confirmation that
  names the group). Errors `group_in_use`, `group_has_children`,
  `group_cycle` translated.
- **Places:** leaders see "Add place" on the places page and in the
  activity and event forms (a small inline form: name, address); "Edit" only
  on their own places and for club managers.
- **Club settings page** (`/clubs/:clubId/settings`, club managers): time
  zone (a searchable select of IANA zones), email, postal address,
  organisation number, phone numbers (add, edit, remove, reorder rows),
  default language.
- **Preferences** (web and mobile): the time zone is a select with "The
  club's time zone" first (null), then the IANA zones grouped by region;
  each error shows its own message.
- **Answers:** the answer form uses two real choices (segmented buttons or
  radio buttons: "Coming" / "Not coming") and a separate "Save" button; the
  note is a textarea pre-filled with the current note, and Enter never picks
  an answer. Clearing the note is explicit. In the leaders' answers table,
  each participant row gets the same two-button control (one form per row,
  works without JavaScript); the row shows "answered by <leader>" when a
  leader set it. Mobile: the same control on the leader's list.
- **Waiting lists and join requests:** the start page and `/me` show "On the
  waiting list for F2017 (number 3 of 8)" and pending join requests with the
  preferred group, for the user and their wards.
- **Joining with a code:** a public page `/join` with a code field (and
  `/join?code=XXXX` from a link): it looks the code up, shows the club, and
  sends people without a login to sign-up with the code kept (cookie or
  `returnTo`), then accepts it after the profile is complete. Logged-in
  members of other clubs get the code field on `/me` too.
- **MFA in development:** with DEV_AUTH, the `mfa_required` message adds
  "Log in again with the MFA box ticked" and a link to the login page with
  the box pre-ticked. No requirement is relaxed (`docs/security.md`); the
  production behaviour is unchanged.

## Privacy and security
- Leaders answering for members is a change to personal data on the
  person's behalf: audited with the leader as actor, visible as "answered by"
  to the family and the leaders. Notes written by a leader are leader notes
  (the same visibility as now).
- Club contact details are the club's, not personal data; phone numbers are
  shown to members only (not on public club pages) unless a later prompt
  adds a public flag.
- Deleting a group is only possible for unused groups, so no personal data
  is lost; archived groups keep their history.
- `pnpm dev:idp-sync` refuses to run unless `NODE_ENV=development` and the
  issuer is the local Zitadel.

## Protected identity
Rosters, answers tables and waiting-list views keep going through
`PersonPresenter`; sorting by given name must not reveal hidden people (the
sort runs on the rows the viewer may see).

## Locale and country packs
New strings in sv, en and nb. Organisation number validation per country
pack (`se`: 10 digits, Luhn on the last; `no`: 9 digits). Time zone names
as `Intl` gives them, with the city in the viewer's language where `Intl`
supports it.

## Performance
Sorting by given name needs the expression index on the roster and
register paths (`EXPLAIN` in the existing query-plan tests). `/me/waitlists`
uses `group_waitlist_entries (person_id)`. No new hot paths otherwise.

## Acceptance criteria
- [ ] An event can be saved with only name and start date; end and
      sign-up deadline get their defaults; an end before the start is
      refused next to the field, on the client and by the server, and the
      form keeps its values.
- [ ] Any number of sessions (up to 20) and questions (up to 20) can be
      added in the browser; "Other" sessions carry a label shown in
      calendars.
- [ ] Rosters, the register (default), answers, attendance and
      registrations list given name first.
- [ ] Groups can be created, edited (all fields), archived, restored and,
      when unused, deleted, by club managers and owners as the policies say.
- [ ] Leaders add places and edit only their own; club managers edit all;
      everyone in the club can pick any active place.
- [ ] New events are published by default; drafts are easy to find.
- [ ] The `mfa_required` message in development explains the MFA box.
- [ ] A person without an account can start from `/join` with a code and
      end up as a member (or with a join request) of the club.
- [ ] `pnpm dev:idp-sync` exists and a Playwright test logs in with email
      and password.
- [ ] Parents see their child's place on a waiting list and pending join
      requests (Henrik: Viktor).
- [ ] Changing an answer and its note works with the keyboard and the
      mouse; a note is never lost by answering again.
- [ ] The time zone preference is a list with "The club's time zone"; each
      preference error has its own message.
- [ ] Club managers set the time zone, email, address, organisation number
      and phone numbers on a settings page.
- [ ] Leaders answer for participants from the answers table (web and
      mobile), audited.
- [ ] Tenant-isolation test and matrix entries for every new endpoint;
      allow/deny tests for every new or changed policy; audit events for
      every change.
- [ ] Translations complete for sv, en and nb.
- [ ] Docs updated (`domain-model.md`, `development.md`, `seed-data.md`,
      ADR 0034 for location creators, ADR 0035 for leaders' answers, P1.10's
      "What exists already").

## Out of scope
- Group owners, moving groups in a hierarchy beyond the parent field,
  admission and running waiting lists (P1.10).
- Public club pages and which contact details they show.
- Notifications about answers set by leaders (P1.7).

## Open decisions
1. **Default end of an event without an end:** end of the start day, or two
   hours after the start? Recommendation: end of the start day for a date
   only, two hours after a start time.
2. **Deleting groups:** hard delete of unused groups only (recommended), or
   archiving only, as P1.10 planned?
3. **Leaders answering after the deadline:** allowed (recommended, the
   leader knows), or bound by the deadline like members?
