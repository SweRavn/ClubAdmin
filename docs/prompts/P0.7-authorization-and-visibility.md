# P0.7 — Authorization engine and person visibility

## Context
Read first: `CLAUDE.md` (rules 2 and 4), `docs/domain-model.md` (Effective
permissions, Protected identity), `docs/security.md`, `docs/performance.md`,
ADR 0006, ADR 0019, ADR 0022.
What exists already: core domain (P0.5), authentication with request
principal (P0.6).

## Goal
Every endpoint declares a permission that is checked by one engine, derived
from relationships; every person shown anywhere passes through one visibility
service; both are fast and thoroughly tested. The first real read endpoints
prove it end to end.

## Scope

### Relationship set
- For a person, load in **one query** all active relationships:
  club memberships, club roles, group memberships with functions, group
  ownerships (expanded through the group hierarchy), guardianships (as guardian,
  with rights; as ward), employments, support-access grants (operators).
- Cache in Valkey per person with a version key. Domain events from P0.5
  (`membership.*`, `role.*`, `group.owner.*`, `guardianship.*`,
  `group.parent.changed`) bump the version of affected persons (via outbox
  handlers). Per-request memoisation on top.

### Policy engine (`apps/api/src/modules/authorization`)
- Permissions are named constants in `packages/shared/src/permissions.ts`
  (e.g. `club.read`, `club.settings.update`, `club.roles.manage`,
  `group.read`, `group.update`, `group.owners.manage`,
  `group.members.read`, `group.members.manage`, `person.profile.read`,
  `person.profile.update`, `person.protection.set`).
- Policies in code: `definePolicy('group.members.manage', ({ actor, resource }) =>
  actor.isClubManager(resource.clubId) || actor.ownsGroup(resource.groupId))`.
  Helpers: `isClubManager`, `hasClubRole`, `ownsGroup` (incl. ancestors),
  `hasGroupFunction`, `isGuardianOf(personId, right)`, `isSelf`,
  `requiresMfa`.
- Guardian acting for a ward: the request may carry `X-On-Behalf-Of: <personId>`;
  the engine checks the guardianship and right, and sets `app.on_behalf_of`
  so history/audit record both.
- `@Endpoint({ permission, resource })`: the resource loader fetches the
  minimal data needed (club id, group id) before the check. **Startup check
  and unit test fail if any route lacks `permission` or `@Public()`.**
- Denials return 404 for resources the actor may not know exist, 403 otherwise
  (documented rule; default 404 for cross-club access).

### Person visibility (ADR 0022)
- `PersonVisibility.resolve(viewer, clubId, personIds[])` → per person:
  `full`, `protected_visible` (full + icon flag), `hidden`.
  Rules exactly as in `domain-model.md`: protected persons visible only to
  self, guardians, club managers, registrars, and owners/leaders of groups the
  person belongs to; hidden for everyone else.
- Bulk: one query (or cache hit) for the protected set of the club:
  `protected:{clubId}` = global-flag persons who are members + club-flag
  persons; invalidated on `person.protection.changed` and membership changes.
- **Presenters:** `PersonPresenter.present(viewer, clubId, people)` is the only
  place that maps a person row to API output (`PersonSummary` with
  `displayName`, `protected: boolean`, ID; hidden persons are removed from
  lists, and counts are returned separately where needed).
  Actor references in history/audit become `{ kind: 'protected' }` when hidden.
- **Guard:** a lint rule (custom ESLint rule) forbids selecting
  `given_name`/`family_name` columns or returning objects with these fields
  outside `presenters/`; a response-schema test ensures every response schema
  uses `PersonSummary` for people.
- Database backstop: view `app.visible_group_members` used by member-facing
  list queries, filtering protected persons unless `app.viewer_privileged` is
  set by the engine for that transaction.
- Access log: reading a protected person's profile writes
  `audit.events` action `person.protected.viewed`.

### First endpoints
| Method | Path | Permission |
|---|---|---|
| GET | `/api/v1/me/clubs` | authenticated (own data) |
| GET | `/api/v1/clubs/:clubId` | `club.read` |

## Privacy and security
- Field-level filtering in presenters: e.g. members see names of group
  co-members; leaders also see guardians' phone numbers; addresses only for
  managers/registrars.
- Every policy has allow **and** deny tests; a generated matrix test runs the
  personas-style fixture (manager, owner, coach, member, parent, relative,
  outsider, operator) against every endpoint.

## Protected identity
Core of this package. Tests must cover: hidden in member lists for other
members, visible with icon for coach/owner/manager, visible to self and
guardian, masked as actor in history output, excluded from search counts
except as aggregate.

## Performance
- Permission check < 0.2 ms with warm cache; relationship load is one query.
- `GET /groups/:id/members` p95 < 50 ms for a 40-member group, ≤ 3 queries.
- Cache invalidation latency < 1 s after a role change (test).

## Seed data
Fixture builder extended with a "matrix" scenario (one of each role) for the
permission tests.

## Acceptance criteria
- [ ] A route without a declared permission fails startup and the test suite.
- [ ] Permission matrix test passes for all endpoints above.
- [ ] Tenant isolation: actor of club B gets 404 for every club A endpoint.
- [ ] Guardian on-behalf-of works and is recorded in history and audit.
- [ ] Protected-identity tests listed above pass; lint rule catches a fixture that returns names outside a presenter.
- [ ] Role change takes effect on the next request (cache invalidation).
- [ ] Performance budgets above met in the integration benchmark.
- [ ] `docs/domain-model.md` permission table updated to match the implemented policies.
