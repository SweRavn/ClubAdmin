# P0.5 — Core domain schema and services

## Context
Read first: `CLAUDE.md`, **`docs/domain-model.md` (authoritative for this
package)**, ADR 0018, ADR 0019, ADR 0020, ADR 0022, `docs/gdpr.md`.
What exists already: DB foundation with tenancy, history, audit, outbox (P0.4).

## Goal
The core entities and their invariants exist as tables and as module services
with tests, so authentication (P0.6), authorization (P0.7) and seeding (P0.8)
can build on them. **No HTTP endpoints in this package.**

## Scope

### Tables (see `domain-model.md` for columns)
Global: `people`, `accounts`, `guardianships`.
Club-owned (`club_id`, RLS, history): `clubs`*, `club_profiles`,
`club_memberships`, `club_role_assignments`, `groups`, `group_seasons`,
`seasons`, `group_memberships`, `group_owners`, `employments`, `consents`.
(*`clubs` itself is keyed by `id`; its RLS policy is `id = app.current_club_id()`
for club context, plus an explicit policy for the "my clubs" lookup in P0.7.)
Waiting lists, join requests and invitations tables are created here (schema
only) so later packages have stable names: `group_waitlist_entries`,
`join_requests`, `invitations`.

Key constraints:
- `accounts.email`: unique on a normalised form (lower-cased, trimmed;
  `citext` or unique index on `lower(email)`); `person_id` unique.
- `people` has **no email column**. Address must be NULL when
  `protected_identity` is true (check constraint).
- `club_profiles.member_number`: unique per club, assigned from
  `clubs.next_member_number` in the same transaction (row lock; no gaps
  required but no duplicates).
- `groups.parent_group_id` in the same club; no cycles (trigger).
- Validity periods (`valid_from`, `valid_to`) with `valid_to > valid_from`;
  partial indexes on active rows (`valid_to IS NULL`).
- Indexes for hot paths: memberships by `(club_id, person_id)`,
  group memberships by `(club_id, group_id)` and `(person_id)`,
  owners by `(group_id)`, guardianships by `(guardian_person_id)` and
  `(ward_person_id)`.

### Encryption
- `packages/server-kit/crypto`: envelope encryption helpers (AES-256-GCM,
  per-club data keys wrapped by a master key from config). Used for
  `people.personal_identity_number` (stored ciphertext + a keyed hash for
  matching duplicates). History uses `redact` for this column.

### Module services (`apps/api/src/modules/...`)
Each with repository, service, domain events, audit events, unit + integration
tests. Services take an actor context; HTTP comes later.
- **people:** create person (no email), update profile, set/clear global
  protected identity (only self or guardian; audited; event
  `person.protection.changed`), merge duplicates (records merge for 30-day
  undo).
- **accounts:** create account for a person with a verified email
  (rejects duplicates case-insensitively), change email (new address must be
  unused), link an account to an existing account-less person ("give own
  login", ADR 0020; only if the person has no account and has reached
  `own_account_min_age` from the country pack).
- **clubs:** create club (creator becomes `club_manager` and active member in
  the same transaction), update settings, `join_policy`.
- **roles:** assign/end club roles. **Invariant: at least one active
  `club_manager` per club**, enforced in the service and by a deferred
  constraint trigger. Manager hand-over: `proposeHandover`, `acceptHandover`
  (new manager active, old one ended, atomically).
- **groups:** create/update/archive, hierarchy, `admission_mode`, capacity.
  Group owners: add/remove (allowed for club managers; for owners only when the
  club setting allows co-owners — policy check comes in P0.7, here the service
  takes an `allowedBy` argument and tests both paths).
- **memberships:** join club (respects `join_policy`), leave, group membership
  with functions, end memberships (sets `valid_to`, never deletes).
- **guardianships:** create (by guardian for a new child), invite co-guardian
  (pending until accepted), rights flags, end at `adult_age` handled by a
  worker job that flags (not removes) and notifies.
- **club profiles:** created with membership; club-level protected-identity
  flag (managers only, audited).

### Country packs (`packages/country-packs`)
- Interface `CountryPack` with `ageRules` (`consentAge`, `ownAccountMinAge`,
  `adultAge`), `personalIdFormat` (parse/validate/normalise), `localeDefaults`
  (locale, time zone, currency).
- Implement `SE` and `NO` (Swedish personnummer/samordningsnummer checksum;
  Norwegian fødselsnummer checksum). Unit tests use official test numbers only.

## Privacy and security
- No personal data in error messages or logs (tests cover the services' errors).
- Every change above writes an audit event and is captured by history.
- Protected persons: address cannot be stored (DB check + service validation).

## Protected identity
Flags and constraints are created here; visibility rules are applied in P0.7.
Domain event `person.protection.changed` invalidates visibility caches later.

## Locale and country packs
Clubs get `country`, `default_locale`, `time_zone`, `currency` defaults from
the country pack on creation.

## Performance
- Index plan reviewed for: "my clubs and groups" (by person), "members of
  group", "guardians of person", "wards of person".
- `EXPLAIN` snapshots for those queries checked into tests (fail on sequential
  scans with the load-sized fixture introduced in P0.8; for now with 10k rows).

## Seed data
A small fixture builder used by tests (`buildClub()`, `buildPerson()`,
`buildFamily()`); the full demo scenario is P0.8.

## Acceptance criteria
- [ ] All tables migrate; RLS and history CI guards pass.
- [ ] Creating a club makes the creator manager + member; audit and history rows exist.
- [ ] Removing or ending the last manager fails (service and DB trigger, tested separately).
- [ ] Hand-over is atomic: after accept, exactly the new manager is active (test with concurrent attempts).
- [ ] Duplicate email (different case) is rejected; a person never gets an email column.
- [ ] Account-less child can later be linked to a new account with its own email; memberships and history are unchanged.
- [ ] Member numbers are unique per club under concurrent inserts (test).
- [ ] Group hierarchy rejects cycles and cross-club parents.
- [ ] Tenant isolation tests for every club-owned table.
- [ ] `docs/domain-model.md` updated with any column changes made during implementation.

## Out of scope
HTTP endpoints, authorization policies (P0.7), waiting-list behaviour
(P1.10), join-request/invitation flows (P1.1), UI.
