# P1.3b — Adding members by hand and importing them from a file

## Context
Read first: `CLAUDE.md`, `docs/domain-model.md` ("people", "club_profiles",
"club_memberships", "Children without login", "guardianships", "The member
register", "Protected identity"), ADR 0011 (object storage), ADR 0020
(identifiers and login email: people never have an email; the importer moves
a child's email to a guardian), ADR 0022 (protected identity), ADR 0029 (API
only grows), ADR 0031 (club access state), ADR 0032 (transactional email),
`docs/performance.md`, `docs/security.md`, `docs/gdpr.md`, and the P1.3
prompt (guardians, duplicates, own login).

What exists already:
- **Services:** `PeopleService.createPerson` (no email; personal identity
  number encrypted with a blind index, validated by the country pack),
  `MembershipsService.addMember` (administrative add, active at once; the
  profile and its member number are created with it),
  `GuardianshipsService.addGuardian` (a club manager in the ward's club may
  confirm full guardians), `AccountsService.createOwnLoginInvitation` (a
  club manager may invite a person's own email), `ClubProfilesService`
  (shared fields), group memberships. No endpoints for adding members.
- **P1.2:** the member register, `club.members.manage`, the members module;
  object storage through `@clubadmin/server-kit/object-storage` (pre-signed
  links, lifecycle rule for `exports/`), CSV helpers in the worker.
- **P1.3:** guardianship endpoints and UI, duplicate candidates per club,
  merge with undo, guardian and own-login invitation emails.
- **Guardians:** a ward can already have any number of guardians: the only
  constraint is one open guardianship per guardian and ward
  (`guardianships_open_unique`); kinds are `parent`, `legal_guardian`,
  `relative`, `contact_person`. Nothing in the API or the presenters
  assumes two.

## Goal
A club moving to ClubAdmin brings its members in an afternoon: the
registrar uploads the spreadsheet from the old system (or IdrottOnline), maps
the columns, sees what will happen to every row, fixes or skips the problem
rows and confirms; members, children, guardians (as many as each child has),
groups and membership dates are created, and the guardians can be invited to
log in. Single members from a paper application are added by hand the same
way. No person is ever silently linked to someone outside the club.

## Users and roles involved
Registrars and club managers (add, import), the members and guardians who are
created (and invited), the club's managers (told about every import).

## User stories
- As a registrar, I want to add a member by hand (name, birth date or
  personal identity number, gender, phone, address, membership type, start
  date, groups), so I can register a paper application.
- As a registrar, I want to add a child with any number of guardians (new
  people without login, or members already in the club), and invite the
  guardians by email to log in.
- As a registrar, I want to upload a CSV or Excel file, map its columns
  (automatically for known formats), preview every row (new member, possible
  duplicate in the club, error with the reason) and confirm, so the import
  is predictable.
- As a registrar, I want to re-run an import with a corrected file without
  creating duplicates of the rows that were already imported.
- As a club manager, I want to know when someone imports members (who, how
  many) and see the import's report.
- As a parent who is imported, I want an invitation email that explains who
  added me and why, and I want my child's data linked to my own login if I
  already have one (after I accept, never automatically).

## Any number of guardians
Already true in the data model; this package makes sure it stays true
everywhere and covers the common family shapes:
- Manual add and import accept any number of guardians per child (import:
  repeated column groups `guardian 1 …`, `guardian 2 …`, … without an upper
  limit, or one row per guardian with a shared family key).
- New guardianship kinds, added to the enum (ADR 0029: clients show unknown
  values as "Other"): `step_parent` (bonus parent) and `foster_parent`
  (family home). Both behave like `relative` (P1.3): they are linked kinds
  with rights chosen per link, default `view_schedule` only, never full
  guardians. Their rights are changed by a full guardian (`parent`,
  `legal_guardian`) of a minor, or by the young person themselves from the
  country pack's `consentAge` (with their own login); `act_on_behalf`
  only when explicitly ticked by a full guardian or the adult ward, with
  the warning, as for relatives. Add them to `LINKED_GUARDIANSHIP_KINDS`
  and `DEFAULT_GUARDIANSHIP_RIGHTS`, so the P1.3 rules (who links, who
  changes rights, who ends, the adult decision) apply unchanged. Update the
  domain model's kind list, the shared constants, the check constraints
  (forward-only migration), the translations and `profileAccess`/policies
  where kinds are listed.
- Tests with a child who has four guardians (two parents, a step-parent, a
  grandparent): the register, the profile, the CSV export, invitations,
  `X-On-Behalf-Of` and merges handle all four.
- The UI never says "the other parent" or "second guardian"; lists show all
  guardians.

## Data model
- `member_imports` (club-owned, tenant RLS, history, `updated_at`):
  `created_by_person_id`, `status` (`uploaded`, `parsing`, `review`,
  `importing`, `done`, `failed`, `cancelled`), `source_format` (`csv`,
  `xlsx`), `column_map` (JSON: file column → field), `options` (default
  membership type, start date when missing, member numbers: keep or assign,
  send invitations), `counts` (JSON: rows, new, duplicate, error, skipped,
  imported), `object_key` (the uploaded file, deleted after parsing),
  `error_code`, `confirmed_at`, `finished_at`. Person reference declared in
  `members.references.ts`.
- `member_import_rows` (club-owned, tenant RLS; **no history**, listed in
  `history-exclusions.ts` with the reason: staging data deleted after seven
  days): `import_id`, `row_number`, `data` (JSON: the parsed values,
  personal data; the personal identity number encrypted with the field
  encryption helpers, never plain), `status` (`new`, `duplicate`, `error`,
  `skipped`, `imported`), `issues` (codes, never values), `person_id` (after
  import), `family_key`.
- Index `member_import_rows (import_id, row_number)`; the register's
  indexes cover duplicate checks.
- Retention: staging rows and the uploaded file are deleted seven days after
  the import finishes or is cancelled (worker); the `member_imports` row
  (counts only) stays as a record.
- No email column on people (ADR 0020): emails from the file are used only to
  send invitations and are kept only in the invitation rows.

## API
All under `/api/v1/clubs/:clubId`.

| Method | Path | Permission | Notes |
|---|---|---|---|
| POST | `/members` | `club.members.add` | Add one person by hand (fields above; optional guardians: existing members by ID or new people; optional own-login or guardian invitations); returns the register row |
| POST | `/member-imports` | `club.members.import` | Starts an import: returns a pre-signed upload URL (PUT, 10 MB, 15 minutes) under `imports/<club_id>/` |
| POST | `/member-imports/:importId/uploaded` | `club.members.import` | The file is uploaded: the worker parses it (`members:import_parse`) |
| GET | `/member-imports/:importId` | `club.members.import` | Status, detected columns, suggested mapping, counts |
| PUT | `/member-imports/:importId/mapping` | `club.members.import` | Column map and options; re-validates (worker) |
| GET | `/member-imports/:importId/rows?status=&cursor=` | `club.members.import` | Preview rows with issues, keyset by row number; names only through the presenter of the importing user's view |
| PATCH | `/member-imports/:importId/rows/:rowNumber` | `club.members.import` | Skip or un-skip a row; mark a duplicate as "same person" (use the existing member) or "different person" |
| POST | `/member-imports/:importId/confirm` | `club.members.import` | Recent login; the worker imports (`members:import_run`) |
| POST | `/member-imports/:importId/cancel` | `club.members.import` | Before confirmation |
| GET | `/member-imports` | `club.members.import` | The club's imports (who, when, counts), keyset |

Problem codes for expected failures (`import_file_too_large`,
`import_format_unsupported`, `import_not_in_review`, …), never values.

## Permissions
New permissions, one policy each, allow and deny tests, entries in the
permission matrix (tenant isolation: 404 for club B):
- `club.members.add`: registrars; club managers (MFA).
- `club.members.import`: registrars and club managers, with MFA;
  confirming also needs `@RecentAuth(15)`.

## Import rules
- **Formats:** CSV (UTF-8 with or without BOM, Windows-1252; `,` or `;`
  detected) and XLSX (first sheet), parsed in the worker, streaming. An XLSX
  library only if its licence is on the allow list (`docs/licensing.md`)
  and it parses without evaluating formulas; otherwise CSV only and say so
  in the UI.
- **Column mapping:** headers recognised in sv, en and nb and from the
  IdrottOnline member export (country pack `se`); unknown columns ignored
  (shown in the preview).
- **Fields:** given and family name, birth date or personal identity number
  (validated by the country pack; the birth date must match), gender,
  phone, address, email, membership type, start date (`valid_from`),
  member number (keep if unique in the club, else error; or assign new),
  groups (by name; must exist, no groups are created), guardians (any
  number: name, phone, email, kind).
- **Emails (ADR 0020):** an adult's email becomes an own-login invitation (if
  chosen); a minor's email is never stored on the child: it is offered as a
  guardian's email when the row has a guardian without one, else dropped
  with an issue code.
- **Duplicates:** within the club only (personal identity number hash,
  else birth date + family name + given name): the preview offers "same
  person" or "different person". People outside the club are never matched
  or revealed; possible duplicates across clubs are resolved later by the
  people themselves (merge, P1.3).
- **Idempotency:** a re-run with the same file and mapping skips rows whose
  person already exists in the club with the same key (personal identity
  number hash or name + birth date) and reports them as skipped.
- **Writing:** every row through the services (person, profile, membership,
  group memberships, guardianships) in batches of 100, each batch one
  transaction with audit events; a failed batch is reported and the rest
  continues; nothing is half-imported within a row.
- **Invitations:** only after confirmation and only if chosen; rate-limited
  per club per day; the email says which club added them and why.

## UI (web)
- Register (P1.2): "Add member" form (person, membership, groups,
  guardians: "Add guardian" repeatable without limit, existing member or
  new person, kind, optional email for an invitation).
- `/clubs/[clubId]/members/import`: upload, mapping (dropdowns with
  detected columns and a sample value per column), preview (counts per
  status, filter by status, row issues in plain words, skip, same/different
  person), confirm with a summary ("312 new members, 280 guardians, 41
  invitations will be sent"), progress and the report; list of past
  imports.
- Loading, empty and error states; translations in sv, en, nb.

Mobile is out of scope.

## Privacy and security
- The uploaded file is personal data at rest: under the club's prefix,
  never public, deleted after parsing (and by a lifecycle rule for
  `imports/` after two days); staging rows deleted after seven days;
  personal identity numbers encrypted in staging too.
- Audit: `members.import.started`, `.confirmed`, `.finished` (counts, never
  values) and the usual per-person events from the services; every club
  manager is emailed when an import finishes (who, counts).
- Formula injection is irrelevant for input but values are stored as
  plain text; no cell content is ever evaluated.
- File size and row limits (10 MB, 20,000 rows) and parse time limits in
  the worker; malformed files fail with a code, not a stack trace.
- Logs carry IDs and counts only, never row contents.

## Protected identity
Rows can carry a protected flag (column or set in the preview): the person
is created with the club-level flag (`protected_identity_club`) and no
address is stored. The preview shows such rows only to the importing
registrar or manager (who may see protected members). Invitations to a
protected person's guardians never name the child to anyone else.

## Locale and country packs
Strings in sv, en, nb. Header recognition and personal identity number
validation per country pack; IdrottOnline column names in `se`. Dates in
the file: ISO and the club's locale format (`2017-04-02`, `02.04.2017`,
`2/4/2017` only when unambiguous for the locale).

## Performance
Parsing 10,000 rows < 30 s; importing 10,000 members with guardians < 3
minutes in the worker (batches, no N+1 within a batch); the preview pages
with keyset pagination (< 100 ms); duplicate checks use the register's and
people's indexes (query-plan test on the load scenario's large club).

## Seed data
- One finished import in FIL (Lars, a handful of rows) with its report, and
  one in review in IKN with a duplicate and an error row, so the preview can
  be tried.
- A sample CSV in `docs/demodata/imports/` (Swedish headers, `;`
  separator, Windows-1252) with a child who has four guardians.
- Update `seed-data.md`.

## Acceptance criteria
- [ ] A registrar adds a child with three guardians by hand; all three see
      the child after accepting their invitations.
- [ ] The sample file imports: children, guardians (four for one child),
      groups and start dates; re-running it skips every row.
- [ ] Duplicates within the club are offered, never people outside it.
- [ ] A minor's email ends up as an invitation to a guardian, never on the
      child.
- [ ] `step_parent` and `foster_parent` work end to end with the default
      rights of a relative (`view_schedule`); a parent and a young person
      from the consent age change them, nobody else; older clients show
      them as "Other".
- [ ] Staging rows and files are deleted on schedule; personal identity
      numbers are never stored in plain text.
- [ ] Import budgets met (worker test on 10,000 rows).
- [ ] Tenant-isolation test for every new endpoint
- [ ] Allow/deny tests for every new policy
- [ ] Audit events for every change to personal data
- [ ] Translations complete for sv and en (and nb)
- [ ] Docs updated: `domain-model.md` (kinds, imports), `gdpr.md`
      (import retention), `security.md` (uploads), ADR 0011 (pre-signed
      uploads) if the client changes

## Out of scope
- Matching or linking people across clubs on import (privacy).
- Ongoing synchronisation with another system or federation (Phase 2).
- Member fees from the import (Phase 3); the `members_max` entitlement
  (P1.13).
- Importing activities, attendance or documents.
